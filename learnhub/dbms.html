1. What is a DBMS?

Data is raw facts (like "Aarav", "84"). Information is data with meaning ("Aarav scored 84"). A database is an organised collection of data. A DBMS (Database Management System) is the software that stores, retrieves and protects it. Think of a library: books are data, shelves are the database, and the librarian is the DBMS.

Advantages and disadvantages

  • Advantages: less redundancy, data sharing, integrity, security, backup and recovery, multi-user access, standard language (SQL).
  • Disadvantages: costly software and hardware, complexity, needs trained staff, overkill for tiny single-user apps, a failure can affect everything.

Key terms: schema and instance

  • Schema: the design or blueprint of the database (table names, columns, types). It changes rarely.
  • Instance: the actual data stored at one moment (a snapshot). It changes constantly.
  • Data dictionary (catalog): the DBMS's own tables that store information about the data (metadata).

3-Schema Architecture

  • External (view) level: what each user sees.
  • Conceptual (logical) level: tables, relationships, constraints for everyone.
  • Internal (physical) level: how data is stored on disk (files, indexes).
User A view   User B view   User C view      (External level)
        \           |           /
         +----- Conceptual schema -----+            (Logical level)
                      |
              Internal schema                      (Physical level)
                      |
                    Disk
💡 Data independence: you can change a lower level without breaking the upper one. Physical independence = change storage without changing tables. Logical independence = change tables without changing user views (harder to achieve).

DBMS components (what is inside)

  • Query processor: DDL compiler, DML compiler, query optimiser (finds the cheapest way to run a query).
  • Storage manager: file manager, buffer manager (keeps hot pages in RAM), transaction manager, authorisation manager.
  • Disk storage: data files, indexes, data dictionary, log files.

People who use a database

  • DBA (Database Administrator): installs, tunes, backs up, secures, grants access.
  • Database designer: decides tables and relations.
  • Application programmers and end users (casual, naive, sophisticated).

Data models and languages

Data models: hierarchical (tree), network (graph), relational (tables, the most used), object-oriented, document, key-value, graph. Languages: DDL (define), DML (manipulate, procedural or declarative), DCL, TCL. SQL is declarative: you say what you want, not how to get it.

Types of databases

Relational (SQL): MySQL, PostgreSQL, Oracle, SQL Server. NoSQL: MongoDB (document), Redis (key-value), Cassandra (column), Neo4j (graph).

2. ER Model, Relational Model & Keys

Before building tables we draw the design as an ER (Entity-Relationship) diagram.

  • Entity (rectangle): a real-world thing, such as Student, Course. A group of similar entities is an entity set.
  • Attribute (oval): a property, such as name, phone. Underlined = key.
  • Relationship (diamond): link between entities, such as Enrolls.

This is a Many-to-Many (M:N) relationship: one student takes many courses, and one course has many students.

Types of attributes

  • Simple: cannot be split (age). Composite: can be split (address → city, pin).
  • Single-valued: one value (roll_no). Multivalued: many values (phone numbers, drawn with a double oval).
  • Derived: calculated (age from date of birth, dashed oval). Stored: the base value (date of birth).

Cardinality and participation

  • Cardinality = how many entities can be linked: 1:1, 1:N, N:1, M:N.
  • Participation = must every entity take part? Total (double line, mandatory: every Employee works in a Department) or Partial (single line, optional).

Cardinality and converting to tables

RelationshipExampleHow to make tables
1 : 1Person – PassportPut the foreign key on either side (prefer the side with total participation)
1 : NDepartment – StudentsPut the foreign key on the N side
M : NStudent – CourseCreate a new table (Enrollment) with both keys
✍️ Worked example: converting the diagram above into tables

1. Strong entity → table: Student(roll_no, name), Course(course_id, title, credits).
2. Multivalued attribute phone → its own table: Student_Phone(roll_no, phone) with roll_no as foreign key.
3. M:N relationship → table with both keys plus relationship attributes: Enrolls(roll_no, course_id, grade).
Total: 4 tables. The composite primary key of Enrolls is (roll_no, course_id), and each part is also a foreign key.

Weak entity: cannot be identified alone, depends on a strong entity (example: Dependent of Employee). It has a partial key (discriminator), is drawn with a double rectangle, and its table's primary key = owner's key + partial key.

Extended ER: Specialization, Generalization, Aggregation

  • Specialization (top-down): split an entity into sub-types. Employee → Engineer, Manager (an "ISA" relationship). Sub-types inherit attributes.
  • Generalization (bottom-up): combine similar entities into one super-type (Car + Truck → Vehicle).
  • Constraints: disjoint (an entity belongs to only one sub-type) vs overlapping; total vs partial coverage.
  • Aggregation: treat a relationship as a higher-level entity so it can take part in another relationship.

Properties of a relation: no duplicate rows, row order does not matter, column order does not matter, every value is atomic.

Keys

📌 Example: in Student(roll_no, email, name), both roll_no and email are candidate keys. If we pick roll_no as primary, then email is an alternate key. {roll_no, name} is a super key but not a candidate key.
💡 Counting trick: in a relation with n attributes, if there is exactly one candidate key and it is a single attribute, the number of super keys is 2n−1 (the key plus any combination of the other n−1 attributes).

Integrity constraints

Entity integrity: primary key cannot be NULL. Referential integrity: a foreign key must match an existing primary key (or be NULL). Domain: values must be of the right type or range. Key constraint: keys are unique.

Referential actions (what happens when the parent row is deleted or updated):

Creating a table with constraints

CREATE TABLE students (
  id       INT PRIMARY KEY,
  name     VARCHAR(50) NOT NULL,
  email    VARCHAR(80) UNIQUE,
  marks    INT CHECK (marks BETWEEN 0 AND 100),
  dept_id  INT,
  FOREIGN KEY (dept_id) REFERENCES departments(id)
);

INSERT INTO students VALUES (9, 'Neha', 'neha@x.com', 84, 1);
UPDATE students SET marks = 90 WHERE id = 9;
DELETE FROM students WHERE id = 9;

Other constraints: DEFAULT value, AUTO_INCREMENT (MySQL) / SERIAL (PostgreSQL), and ON DELETE CASCADE on a foreign key.

Changing a table (ALTER)

ALTER TABLE students ADD city VARCHAR(30);
ALTER TABLE students MODIFY name VARCHAR(80);   -- MySQL
ALTER TABLE students DROP COLUMN city;
ALTER TABLE students ADD CONSTRAINT uq_email UNIQUE (email);
💡 DELETE removes rows (can WHERE, can rollback). TRUNCATE removes all rows quickly (no WHERE, resets auto-increment, usually cannot rollback). DROP removes the whole table and its structure.

Useful operators and clauses

SELECT DISTINCT dept_id FROM students;
SELECT * FROM students WHERE marks BETWEEN 60 AND 80;
SELECT * FROM students WHERE dept_id IN (1, 2);
SELECT * FROM students WHERE name LIKE 'A%';    -- % any text, _ one character
SELECT * FROM students ORDER BY marks DESC, name ASC LIMIT 5;
SELECT name, marks + 5 AS bonus_marks FROM students;

Aggregate functions and GROUP BY

COUNT, SUM, AVG, MIN, MAX turn many rows into one value. GROUP BY makes one result row per group. Every column in SELECT must be either grouped or inside an aggregate.

SELECT dept_id, COUNT(*) AS total, AVG(marks) AS avg_marks
FROM students
GROUP BY dept_id;

✍️ Worked example: INNER vs LEFT vs RIGHT join

students: (Aarav, dept 1), (Priya, dept 2), (Isha, NULL)
departments: (1, CSE), (2, ECE), (3, Civil)

INNER JOIN on dept id → Aarav–CSE, Priya–ECE (2 rows). Isha has no match and Civil has no match, so both are dropped.
LEFT JOIN (students on the left) → Aarav–CSE, Priya–ECE, Isha–NULL (3 rows).
RIGHT JOIN → Aarav–CSE, Priya–ECE, NULL–Civil (3 rows).
FULL JOIN → all 4 distinct combos above (Isha–NULL and NULL–Civil both appear).

-- Self join: employee with manager name
SELECT e.name AS employee, m.name AS manager
FROM emp e LEFT JOIN emp m ON e.manager_id = m.id;

WHERE vs HAVING, and the order SQL runs

WHERE filters rows before grouping. HAVING filters groups after GROUP BY (works with COUNT, SUM, AVG).

Written:  SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
Runs as:  FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

Subqueries, IN, EXISTS, ANY, ALL

A subquery is a query inside a query. A correlated subquery uses a value from the outer query and runs once per outer row.

-- Students who scored above the average
SELECT name FROM students WHERE marks > (SELECT AVG(marks) FROM students);

-- Departments that have at least one student
SELECT dept_name FROM departments d
WHERE EXISTS (SELECT 1 FROM students s WHERE s.dept_id = d.id);

-- Higher than ALL students of dept 2
SELECT name FROM students
WHERE marks > ALL (SELECT marks FROM students WHERE dept_id = 2);
📌 IN compares to a list of values. EXISTS only checks whether any row comes back (stops at the first match, often faster for big subqueries). Beware: NOT IN returns nothing if the list contains a NULL, so prefer NOT EXISTS.

Set operations

UNION merges results and removes duplicates; UNION ALL keeps duplicates (faster); INTERSECT common rows; EXCEPT (MINUS in Oracle) rows in the first but not the second. Both queries need the same number and type of columns.

CASE, and NULL handling

SELECT name,
  CASE WHEN marks >= 90 THEN 'A'
       WHEN marks >= 75 THEN 'B'
       ELSE 'C' END AS grade
FROM students;

SELECT COALESCE(dept_id, 0) FROM students;   -- first non-NULL value
📌 NULL tip: NULL is "unknown". NULL = NULL is not true. Always use IS NULL. Also COUNT(*) counts all rows, but COUNT(col) skips NULLs, and aggregates like AVG ignore NULLs.

Window functions and CTEs (modern SQL)

A window function calculates across related rows without collapsing them into one row like GROUP BY does.

SELECT name, marks,
  ROW_NUMBER() OVER (ORDER BY marks DESC) AS rn,
  RANK()       OVER (ORDER BY marks DESC) AS rnk,
  DENSE_RANK() OVER (ORDER BY marks DESC) AS drnk
FROM students;

-- CTE (a named temporary result, easier to read than nested subqueries)
WITH top AS (SELECT * FROM students WHERE marks >= 85)
SELECT name FROM top;

Classic placement queries

-- 2nd highest marks
SELECT MAX(marks) FROM students
WHERE marks < (SELECT MAX(marks) FROM students);

-- Nth highest (N = 3) using LIMIT/OFFSET
SELECT DISTINCT marks FROM students ORDER BY marks DESC LIMIT 1 OFFSET 2;

-- Duplicate emails
SELECT email, COUNT(*) FROM students GROUP BY email HAVING COUNT(*) > 1;

-- Delete duplicates but keep one row (keeps the smallest id)
DELETE FROM students WHERE id NOT IN (
  SELECT MIN(id) FROM (SELECT id, email FROM students) t GROUP BY email);

-- Students with no department
SELECT name FROM students WHERE dept_id IS NULL;

-- Departments with more than 2 students
SELECT d.dept_name, COUNT(*) FROM departments d
JOIN students s ON s.dept_id = d.id
GROUP BY d.dept_name HAVING COUNT(*) > 2;

-- Departments with NO students
SELECT d.dept_name FROM departments d
LEFT JOIN students s ON s.dept_id = d.id
WHERE s.id IS NULL;

-- Highest marks in each department
SELECT dept_id, MAX(marks) FROM students GROUP BY dept_id;

-- Employees earning more than their manager
SELECT e.name FROM emp e JOIN emp m ON e.manager_id = m.id
WHERE e.salary > m.salary;
💡 Tip for the duplicate-delete query: in MySQL you cannot select from the same table you are deleting from directly, so the inner query is wrapped as a derived table (t).

4. Normalization & Functional Dependencies

Normalization means organising tables to remove redundancy and avoid anomalies by splitting big tables into smaller related ones.

Why? The 3 anomalies

Student_Course (roll, name, course, instructor)
101 | Aarav | DBMS | Rao
101 | Aarav | OS   | Iyer
102 | Priya | DBMS | Rao
  • Insert anomaly: cannot add a new course until a student enrolls.
  • Update anomaly: if Rao changes name, we must edit many rows.
  • Delete anomaly: deleting Priya also deletes the fact that DBMS is taught by Rao.

Functional Dependency (FD)

X → Y means: if two rows have the same X, they must have the same Y. Example: roll → name. X is the determinant.

KindMeaningExample
TrivialY is a subset of X{roll, name} → name
Non-trivialY is not a subset of Xroll → name
Full dependencyY depends on the whole composite key(roll, course) → grade
Partial dependencyY depends on part of a composite key(roll, course) → name, because roll → name
Transitive dependencyX → Y and Y → Z, so X → Z through a non-keyemp → dept → dept_head

Armstrong's axioms (rules to derive FDs)

  • Reflexivity: if Y ⊆ X then X → Y.
  • Augmentation: if X → Y then XZ → YZ.
  • Transitivity: if X → Y and Y → Z then X → Z.
  • Derived: Union (X→Y, X→Z ⇒ X→YZ), Decomposition (X→YZ ⇒ X→Y and X→Z), Pseudo-transitivity (X→Y, WY→Z ⇒ WX→Z).

Closure and candidate keys

The closure X⁺ is the set of all attributes that X can determine. Method: start with X, keep adding the right side of any FD whose left side is already inside, until nothing new appears. If X⁺ contains all attributes, X is a super key; if no proper subset of X is also a super key, X is a candidate key.

✍️ Worked example: R(A,B,C,D,E), FDs: A→B, BC→D, D→E. Find the candidate key.

Step 1: attributes that never appear on any right side must be in every key. Right sides: B, D, E. So A and C must be in the key.
Step 2: compute (AC)⁺: start {A, C} → A→B gives {A,B,C} → BC→D gives {A,B,C,D} → D→E gives {A,B,C,D,E}. That is all attributes.
Step 3: A⁺ = {A,B} and C⁺ = {C}, so no smaller part works.
Candidate key = AC (and it is the only one).

Normal forms

FormRuleFixes
1NFEvery cell has a single (atomic) value, no repeating groupsMulti-valued cells
2NF1NF + no partial dependency (non-key attribute must depend on the whole key)Needs a composite key to matter
3NF2NF + no transitive dependency. Formally: for every X → A, either X is a super key or A is a prime attribute (part of some candidate key)Key → A → B
BCNFFor every FD X → Y, X must be a super keyStricter 3NF
💡 Remember: "The key (1NF), the whole key (2NF), and nothing but the key (3NF/BCNF), so help me Codd."

4NF removes multi-valued dependencies (X →→ Y), 5NF removes join dependencies. They are rarely asked in depth. Hierarchy: BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF.

Examples for each form

✍️ 1NF: multi-valued cell

Not in 1NF: Student(101, Aarav, "9876, 9123") has two phones in one cell.
Fix: one row per phone, (101, Aarav, 9876) and (101, Aarav, 9123), or better, move phones to a separate table.

✍️ 2NF: partial dependency

R(StudentID, CourseID, StudentName, Grade). Key = (StudentID, CourseID).
StudentID → StudentName is a partial dependency (name depends on only part of the key).
Fix: split into Student(StudentID, StudentName) and Enrollment(StudentID, CourseID, Grade).

✍️ 3NF: transitive dependency

R(Emp, Dept, DeptHead) with Emp → Dept and Dept → DeptHead. So Emp → DeptHead is transitive.
Fix: Employee(Emp, Dept) and Department(Dept, DeptHead).

✍️ BCNF: 3NF but not BCNF

R(A,B,C) with FDs AB → C and C → A. Candidate keys: AB and BC (AB⁺ = ABC; BC⁺ = BCA). All attributes are prime, so the relation is in 3NF (A is prime in C → A). But C is not a super key, so it is not in BCNF.
Decompose to R1(C, A) and R2(B, C). Now every determinant is a key, but the dependency AB → C is no longer stored in one table (BCNF can lose dependency preservation).

Decomposition: what makes it good?

  • Lossless join: joining the pieces back gives exactly the original data. Test: for a split into R1 and R2, the common attributes must be a key of R1 or R2.
  • Dependency preserving: every original FD can still be checked inside one of the smaller tables.
  • 3NF can always be reached with both properties. BCNF always gives lossless join but may lose dependencies.

📌 Closure X⁺ = all attributes that X can determine. If X⁺ contains every attribute, X is a super key. Try attributes A B C with FDs AB -> C and C -> A to see BCNF vs 3NF.

Denormalization

Sometimes we add redundancy back on purpose to make read-heavy queries faster (fewer joins). This is a trade-off: faster reads, harder updates. Common in reporting and data warehouses.

5. Transactions, Concurrency & Recovery

A transaction is a group of operations treated as one unit. Example: transferring money (debit A, credit B).

Transaction states

Active → Partially Committed → Committed. If something fails: Active/Partially Committed → Failed → Aborted (rolled back, and then either restarted or killed).

Active --> Partially Committed --> Committed
  |                |
  +--> Failed <----+

Concurrency problems

  • Dirty read: reading data written by an uncommitted transaction (W–R conflict).
  • Non-repeatable read: reading the same row twice gives different values (R–W conflict).
  • Phantom read: the same query returns new rows the second time.
  • Lost update: two transactions overwrite each other's changes (W–W conflict).

Isolation levels

Read UncommittedPossiblePossiblePossible

📌 Higher isolation = more correctness but less concurrency (slower). Defaults: MySQL InnoDB = Repeatable Read, PostgreSQL and Oracle = Read Committed.

Schedules and serializability

A schedule is the order in which operations of several transactions run. A serial schedule runs one transaction fully after another (always correct, but slow). A schedule is serializable if its result equals some serial order.

Two operations conflict when they are from different transactions, on the same data item, and at least one is a write. Conflict serializability is checked with a precedence graph: draw an edge Ti → Tj if a conflicting operation of Ti comes before one of Tj. No cycle → conflict serializable.

✍️ Worked example: two schedules

S1: R1(A), W1(A), R2(A), W2(A)
Conflicts: W1(A) before R2(A) and W2(A), and R1(A) before W2(A). All edges point T1 → T2. No cycle → serializable, equivalent to the serial order T1, T2.

S2: R1(A), R2(A), W1(A), W2(A)
R2(A) before W1(A) gives T2 → T1. R1(A) before W2(A) gives T1 → T2. These form a cycle → not conflict serializable (it is also a lost-update situation).

Recoverable schedules

  • Recoverable: if Tj reads from Ti, then Ti must commit before Tj commits.
  • Cascadeless (ACA): transactions read only committed data, so no chain of rollbacks.
  • Strict: no read or write of an item until the transaction that last wrote it commits or aborts. Strict ⊂ Cascadeless ⊂ Recoverable.

Locking

  • Shared lock (S): for reading, many allowed. Exclusive lock (X): for writing, only one.
  • Two-Phase Locking (2PL): a growing phase (only take locks), then a shrinking phase (only release). It ensures serializability but can cause deadlock. Strict 2PL holds exclusive locks until commit, which avoids cascading rollbacks. Rigorous 2PL holds all locks until commit.
  • Timestamp ordering: older transactions get priority, with no locks.
  • MVCC (Multi-Version Concurrency Control): keep several versions of each row, so readers see an old snapshot and never block writers (PostgreSQL, Oracle, MySQL InnoDB).
  • Lock granularity: row, page, table. Finer locks = more concurrency but more overhead.

Deadlock in databases

T1 holds a lock on A and waits for B; T2 holds B and waits for A. Handling:

  • Detection: build a wait-for graph; a cycle = deadlock; abort one victim.
  • Wait-Die (non-preemptive): if an older transaction wants a lock held by a younger one, it waits; if a younger one wants a lock held by an older one, it dies (aborts).
  • Wound-Wait (preemptive): an older requester wounds (aborts) the younger holder; a younger requester waits.
  • Timeout: abort if waiting too long. Both schemes use timestamps, so the oldest transaction is never starved.

Recovery

Write-Ahead Logging (WAL): the log is written to disk before the data change. After a crash: REDO committed transactions, UNDO uncommitted ones. Checkpoints limit how far back we need to look.

  • Log record examples: <T1 start>, <T1, A, old=1000, new=800>, <T1 commit>.
  • Deferred update: write to the DB only after commit (only REDO needed). Immediate update: write early (UNDO and REDO needed).
  • ARIES is the standard algorithm: analysis, redo, undo. Shadow paging keeps a copy of the page table instead of a log.
  • Backups: full, incremental, differential; point-in-time recovery = restore a backup, then replay the log up to a chosen moment.

6. Indexing, Hashing & Query Performance

An index is like the index at the back of a book. Instead of reading every page (full table scan), you jump straight to the right place.

🏁 Race: with index vs without index

A table has 64 sorted rows. Pick a row number to search for.

A full scan is O(n), while an index lookup is O(log n). With 1 million rows that is about 20 steps instead of up to 1,000,000.

How data sits on disk

Records are stored in fixed-size blocks (pages), and the disk is read one block at a time. Disk I/O is the slow part, so the cost of a query is counted in block accesses.

  • Blocking factor = ⌊block size ÷ record size⌋ (records per block).
  • Number of blocks = ⌈number of records ÷ blocking factor⌉.
  • File organisations: heap (unsorted, fast insert), sorted (fast binary search), hashed (fast equality lookup).
✍️ Worked example: cost of a search with and without an index

30,000 records, record size = 100 bytes, block size = 1024 bytes.
Blocking factor = ⌊1024 ÷ 100⌋ = 10 records/block. Blocks = 30,000 ÷ 10 = 3000.
Linear search (unsorted): average 3000/2 = 1500 blocks, worst case 3000.
Binary search (sorted on the key): ⌈log₂ 3000⌉ = 12 block accesses.
Sparse primary index with one entry per block: 3000 entries. Each entry = 16 bytes → 1024 ÷ 16 = 64 entries/block → ⌈3000 ÷ 64⌉ = 47 index blocks. Binary search in the index = ⌈log₂ 47⌉ = 6, plus 1 data block = 7 block accesses.

✍️ Worked example: inserting into a B+ tree (max 3 keys per node)

Insert 10, 20, 30 → one leaf [10 | 20 | 30].
Insert 40 → leaf overflows (4 keys). Split into [10 | 20] and [30 | 40], and copy up 30 into a new root [30].
Insert 50 → goes to the right leaf: [30 | 40 | 50].
Insert 60 → right leaf overflows → split into [30 | 40] and [50 | 60], copy up 50 → root becomes [30 | 50] with three leaves.
The leaves stay linked left to right: [10 20] → [30 40] → [50 60].

Height estimate: if each node holds up to 100 child pointers (fan-out 100), 1 million keys need about log₁₀₀(10⁶) = 3 levels. That is only 3 to 4 disk reads to find any row.

Hashing

A hash function maps a key to a bucket. It gives O(1) for equality (=) but cannot do range queries (>, BETWEEN) or sorting.

  • Static hashing: fixed number of buckets; overflow chains grow when full.
  • Dynamic hashing (extendible, linear): the bucket directory grows as data grows.
  • Collision: two keys hash to the same bucket (solved by chaining or open addressing).

When an index is NOT used (common mistakes)

  • Function on the column: WHERE YEAR(joined) = 2025 (rewrite as a date range).
  • Leading wildcard: LIKE '%son' cannot use a normal index; LIKE 'Ra%' can.
  • Type mismatch: comparing a number column with a string.
  • Composite index (a, b, c) used with a filter only on b or c (breaks the leftmost-prefix rule).
  • Very low selectivity (a column with only a few distinct values), or a tiny table: the optimiser prefers a scan.
EXPLAIN SELECT * FROM students WHERE marks = 90;   -- shows if an index is used
💡 Indexes are not free. They speed up SELECT but slow down INSERT/UPDATE/DELETE and use extra space. Index columns used often in WHERE, JOIN and ORDER BY. Avoid indexing tiny tables or columns with few distinct values.

How a query is executed

  1. Parse the SQL and check syntax and names.
  2. Convert it to relational algebra.
  3. Optimise: try different plans (join order, which index, join method) and pick the lowest estimated cost, using statistics. Rule of thumb: push selections down (filter early), push projections down.
  4. Execute the plan. Join methods: nested loop, hash join, sort-merge join.
ADVANCED

7. Views, Triggers, Relational Algebra, NoSQL & Distributed Databases

Views, procedures, triggers

  • View: a saved query that acts like a virtual table. It gives security and simplicity. A simple view (one table, no aggregates/DISTINCT) is usually updatable. A materialized view stores the result physically for speed and must be refreshed.
  • Stored procedure: saved SQL code you call by name. It is faster, reusable, and can take parameters and change data. A function must return a value and can be used inside SELECT.
  • Trigger: code that runs automatically on INSERT/UPDATE/DELETE, BEFORE or AFTER the event (example: write an audit log).
  • Cursor: processes query results row by row (slow; prefer set-based SQL when possible).
CREATE VIEW top_students AS
SELECT name, marks FROM students WHERE marks >= 85;

-- Stored procedure (MySQL)
DELIMITER //
CREATE PROCEDURE get_top(IN m INT)
BEGIN
  SELECT name, marks FROM students WHERE marks >= m;
END //
DELIMITER ;
CALL get_top(80);

-- Trigger: log every delete
CREATE TRIGGER log_delete AFTER DELETE ON students
FOR EACH ROW
  INSERT INTO audit(student_id, action) VALUES (OLD.id, 'deleted');

CAP Theorem and BASE

A distributed system can guarantee only 2 of 3: Consistency (everyone sees the same data), Availability (always responds), Partition tolerance (works when the network splits). Since partitions happen in real life, the real choice is CP vs AP.

  • CP: stays correct, may refuse some requests during a partition (e.g. HBase).
  • AP: always answers, may return stale data that is fixed later (e.g. Cassandra, DynamoDB).
  • BASE: Basically Available, Soft state, Eventually consistent. The NoSQL counterpart of ACID.

Distributed databases

  • Replication = copies of the same data on many servers (reliability, read speed). Common setup: one primary takes writes, replicas serve reads.
  • Sharding (partitioning) = splitting data across servers (scale). Choose a good shard key to avoid one overloaded "hot" shard.
  • Two-Phase Commit (2PC): a coordinator asks all nodes "can you commit?" (prepare), then tells all to commit or abort. Gives atomicity across servers but can block if the coordinator fails.

A data warehouse collects data from many sources using ETL (Extract, Transform, Load). A star schema has a central fact table (sales amount, quantity) linked to dimension tables (date, product, customer). OLAP operations: roll-up, drill-down, slice, dice, pivot.

Database security

  • Authentication and authorisation: users, roles, GRANT/REVOKE, least privilege.
  • Encryption: at rest (disk) and in transit (TLS). Store passwords as salted hashes, never as plain text.
  • Auditing and backups.

SQL injection: an attacker types SQL as input and the app glues it into a query.

-- Dangerous (string concatenation)
query = "SELECT * FROM users WHERE name='" + input + "'";
-- input:  ' OR '1'='1     →  WHERE name='' OR '1'='1'   (returns everyone!)

-- Safe: parameterised (prepared) statement
SELECT * FROM users WHERE name = ?;   -- value is passed separately
📌 Prevent injection with prepared statements, input validation, least-privilege database accounts, and never showing raw database errors to users.

8. Practice Problems with Answers

Try each one yourself first, then open the answer.

Q1. R(A,B,C,D,E) with A→B, BC→D, D→E. Find (AC)⁺ and the candidate key.

Start {A,C}. A→B gives {A,B,C}. BC→D gives {A,B,C,D}. D→E gives {A,B,C,D,E}. So (AC)⁺ = all attributes. A and C never appear on a right side, so they must be in every key. Candidate key = AC (only one).

Q2. R(A,B,C,D) has only one candidate key, A. How many super keys does it have?

A super key = A plus any subset of the other 3 attributes → 2³ = 8 super keys.

Q3. R(A,B,C,D) with AB→C and C→D. What is the highest normal form?

(AB)⁺ = ABCD, so the key is AB. There is no partial dependency (D depends on C, which is not part of the key), so it is in 2NF. But C → D is transitive: C is not a super key and D is not prime. So it is not in 3NF. Highest normal form = 2NF.

Q4. R(A,B,C) with AB→C and C→A. Is it in 3NF? In BCNF?

Candidate keys: AB and BC, so A, B, C are all prime. 3NF: for C → A, A is prime, so yes, 3NF. BCNF: C is not a super key, so not in BCNF.

Q5. Table A has 5 rows, table B has 4 rows. How many rows does A CROSS JOIN B give? What is the minimum for A LEFT JOIN B?

Cross join = 5 × 4 = 20 rows. A LEFT JOIN keeps every row of A, so it returns at least 5 rows (more if some A rows match several B rows).

Q6. marks column holds 80, NULL, 90, 90. Find COUNT(*), COUNT(marks), COUNT(DISTINCT marks) and AVG(marks).

COUNT(*) = 4 (all rows). COUNT(marks) = 3 (skips NULL). COUNT(DISTINCT marks) = 2 (80 and 90). AVG = (80+90+90)/3 = 86.67 (NULL is ignored, not treated as 0).

Q7. Write a query to list departments that have no students.

SELECT d.dept_name FROM departments d LEFT JOIN students s ON s.dept_id = d.id WHERE s.id IS NULL;
or SELECT dept_name FROM departments d WHERE NOT EXISTS (SELECT 1 FROM students s WHERE s.dept_id = d.id);

Q8. Is S: R1(A), W2(A), W1(A) conflict serializable?

R1(A) before W2(A) gives T1 → T2. W2(A) before W1(A) gives T2 → T1. The precedence graph has a cycle, so it is not conflict serializable.

Q9. A Student–Course relationship is M:N with attribute "grade", and each entity has only simple attributes. How many tables are needed?

3 tables: Student, Course, and a new Enrollment(student_id, course_id, grade) table.

Q10. 30,000 records of 100 bytes each, block size 1024 bytes, sorted file. How many block accesses for a binary search?

Blocking factor = ⌊1024/100⌋ = 10. Blocks = 30,000/10 = 3000. Binary search = ⌈log₂ 3000⌉ = 12 block accesses.

Q11. A B+ tree has a fan-out of 100 and stores 1,000,000 keys. About how many levels?

log₁₀₀(1,000,000) = log(10⁶)/log(10²) = 6/2 = 3 levels.

Q12. T1 reads a row twice. Between the reads, T2 updates the row and commits. Which anomaly is this and which is the lowest isolation level that prevents it?

It is a non-repeatable read. It is prevented by Repeatable Read (and also by Serializable).

🎯 Important Interview Questions

1. DBMS vs RDBMS?

A DBMS stores data in general form (files, hierarchical). An RDBMS stores data in tables with relationships using keys, supports SQL, constraints and ACID (MySQL, PostgreSQL, Oracle).

2. Primary key vs Unique key?

Primary key: unique, cannot be NULL, only one per table. Unique key: values must be unique, usually allows a NULL (database dependent), and many are allowed per table.

3. What is a foreign key?

A column that refers to the primary key of another table, to enforce referential integrity between the two tables.

4. DELETE vs TRUNCATE vs DROP?

DELETE removes selected rows (WHERE allowed, can rollback). TRUNCATE removes all rows quickly and keeps the structure. DROP removes the table itself.

5. WHERE vs HAVING?

WHERE filters individual rows before grouping and cannot use aggregates. HAVING filters groups after GROUP BY and can use aggregates.

6. INNER JOIN vs LEFT JOIN?

INNER JOIN returns only matching rows. LEFT JOIN returns all rows of the left table and matching rows from the right (NULLs where there is no match).

7. What is normalization? Why do we need it?

Organising data into related tables to remove redundancy and insert, update and delete anomalies. Forms: 1NF, 2NF, 3NF, BCNF.

8. 3NF vs BCNF?

3NF allows X → A if X is a super key or A is a prime attribute. BCNF is stricter: X must always be a super key.

9. Explain ACID with an example.

In a bank transfer: Atomicity (debit and credit both happen or neither), Consistency (total money stays the same), Isolation (other transactions do not see half-done work), Durability (after commit, the result survives a crash).

10. What is a deadlock in DBMS and how is it handled?

Two transactions each wait for a lock held by the other. Handled by prevention (wait-die, wound-wait), detection with a wait-for graph (abort a victim), or timeouts.

11. Clustered vs non-clustered index?

Clustered decides the physical order of rows, so only one per table. Non-clustered is a separate structure with pointers to rows, and many are allowed.

12. What is a view? Can we update through it?

A virtual table defined by a query. Simple views (one table, no aggregates or DISTINCT) can be updated, and the change goes to the base table. Complex views usually cannot.

13. Write a query for the 2nd highest salary.

SELECT MAX(salary) FROM emp WHERE salary < (SELECT MAX(salary) FROM emp); or SELECT DISTINCT salary FROM emp ORDER BY salary DESC LIMIT 1 OFFSET 1;

14. SQL vs NoSQL: when to choose which?

Choose SQL for structured data needing strong consistency and joins (banking). Choose NoSQL for flexible or huge, fast-changing data that needs horizontal scaling (feeds, caching, logs).

15. What is data independence and why does it matter?

It means a change at one level of the 3-schema architecture does not force changes at the level above. Physical independence: change storage or indexes without touching the tables. Logical independence: change the table design without breaking user views. It lets the database evolve without rewriting every application.

16. What is a self join? Give an example.

A table joined with itself using two aliases. Example: employee and manager are in the same table: SELECT e.name, m.name FROM emp e LEFT JOIN emp m ON e.manager_id = m.id;

17. IN vs EXISTS?

IN compares a value to a list returned by a subquery. EXISTS only checks whether the subquery returns any row and can stop at the first match. EXISTS is often faster for large subqueries and is safer than NOT IN when NULLs are possible.

18. ROW_NUMBER vs RANK vs DENSE_RANK?

For scores 90, 90, 80: ROW_NUMBER gives 1, 2, 3 (always unique). RANK gives 1, 1, 3 (ties share a rank and leave a gap). DENSE_RANK gives 1, 1, 2 (ties share a rank, no gap).

19. What is a CTE and why use it?

A Common Table Expression (WITH name AS (query)) is a named temporary result used inside one statement. It makes complex queries readable and allows recursive queries (like walking an org chart).

20. Stored procedure vs function vs trigger?

A procedure is called explicitly, can take input/output parameters and change data. A function must return a value and can be used inside a query. A trigger runs automatically when an INSERT, UPDATE or DELETE happens, and cannot be called directly.

21. What is a lossless decomposition?

Splitting a table so that joining the parts gives back exactly the original rows, with no lost or fake rows. For a binary split R1, R2 it is lossless if the common attributes form a key of R1 or R2.

22. How do you find the candidate keys of a relation?

Find attributes that never appear on any right side of an FD (they must be in every key). Compute the closure of that set. If it covers all attributes it is the key; otherwise add other attributes one by one and recompute until the closure is complete, keeping only minimal sets.

23. Which isolation level prevents which anomaly?

Read Committed prevents dirty reads. Repeatable Read also prevents non-repeatable reads. Serializable also prevents phantom reads. The higher the level, the safer but the slower.

24. What is Two-Phase Locking? Does it prevent deadlock?

2PL has a growing phase (acquire locks only) and a shrinking phase (release only), which guarantees conflict serializability. It does not prevent deadlock. Strict 2PL holds exclusive locks until commit to avoid cascading rollbacks.

25. Wait-die vs wound-wait?

Both use timestamps. Wait-die: an older requester waits for a younger holder; a younger requester aborts. Wound-wait: an older requester aborts (wounds) the younger holder; a younger requester waits. Both avoid circular waiting.

26. What is MVCC?

Multi-Version Concurrency Control keeps several versions of a row. Readers see a consistent snapshot from when they started, so reads do not block writes and writes do not block reads. Used by PostgreSQL, Oracle and MySQL InnoDB.

27. Why do databases use B+ trees instead of binary trees or hash tables?

A B+ tree node matches one disk block and holds hundreds of keys, so the tree is very short (3 to 4 levels for millions of rows), meaning few disk reads. Linked leaves make range queries and sorting fast. A hash index handles only equality, and a binary tree would be too deep for disk access.

28. When will the database not use an index?

When a function is applied to the indexed column, when LIKE starts with a wildcard, when types mismatch, when a composite index's leftmost column is missing from the filter, or when the optimiser decides a full scan is cheaper (tiny table or low selectivity).

29. What is SQL injection and how do you prevent it?

An attacker inserts SQL code through user input that the application joins into a query string (for example ' OR '1'='1), so the query does something unintended. Prevent it with prepared (parameterised) statements, input validation, least-privilege database accounts and hiding database error details.

30. Explain the CAP theorem and ACID vs BASE.

In a distributed database you can have only two of Consistency, Availability and Partition tolerance; since network partitions cannot be avoided, you choose CP (stay correct, may refuse requests) or AP (always respond, may be stale). ACID systems (relational) favour strong consistency. BASE systems (many NoSQL) favour availability and eventual consistency.
